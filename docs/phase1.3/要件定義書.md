## 1. このフェーズの目的

### 何を作るか

封神の封印フローに「**保管**」工程を追加し、「封印 → 保管 → 開封」という一連の流れを整備する。

Phase 1.2 までは、封印と同時に保管場所を記録する設計だった。しかし現実の運用では、封印を行った人と保管を行う人が異なる場合や、封印後に時間・場所をあけて保管が行われる場合がある。このような「封印と保管が時系列で分離する」ケースに対応するため、保管を独立した工程として設ける。

### 保管工程の位置づけ

保管とは「封印された物体を、特定の場所に収めた」という事実をデジタルで記録する行為である。保管時に写真を撮影することで、保管状況の証拠を残すことができる。

封印した人が引き続き保管まで行う場合と、別の人が保管を担当する場合の両方に対応する。

## 2. ステータス体系の変更

### 変更前（Phase 1.2 まで）

| ステータス（内部値） | 表示名 | 意味 |
|--------------------|--------|------|
| `sealed` | 未開封 | 封印済み |
| `opened` | 開封済み | 正規手続きで開封された |
| `tampered` | 破損 | QR検証失敗 |

### 変更後（Phase 1.3 から）

| ステータス（内部値） | 表示名 | 意味 |
|--------------------|--------|------|
| `sealed` | 未保管 | 封印はされているが、保管がまだ行われていない |
| `stored` | 保管中 | 封印され、保管まで完了している |
| `opened` | 開封済み | 正規手続きで開封された |
| `tampered` | 異常検知 | 開封操作は行われたが、全QRコードを読み取れなかった。封印後に第三者が触れた痕跡がある可能性を示す |

> **内部値（Firestore保存値）はそのまま維持し、アプリの表示名のみ変更する。** これにより既存データとの互換性を保ちつつ、ユーザーへの表現を正確にする。

> 開封できるのは `stored`（保管中）状態の箱のみ。`sealed`（未保管）状態では開封操作を実行できない。

### `tampered`（異常検知）が発生する条件

`tampered` は開封フロー内でのみ発生する。発生条件は以下の1つのみである。

- 開封操作を実行したユーザーが、登録されている全QRコードを読み取れなかった場合

これは「正規ユーザーが開封しようとしたが、1枚以上のQRシールが既に存在しなかった（剥がされた・破れた）」ことを意味する。封印後から開封操作までの間に、第三者が物体に触れた可能性を示す状態である。

## 3. 実装する機能

### 3-1. 封印フローへの保管ステップの追加

封印完了後、続けてその場で保管まで行うかどうかをユーザーが選択できるようにする。

**封印完了後のフロー**

```
封印完了
  │
  ├─ 「続けて保管する」を選択
  │     └─ 保管画面へ進む → 保管完了 → ステータスが「保管中」になる
  │
  └─ 「あとで保管する」を選択（またはスキップ）
        └─ ホームへ戻る → ステータスは「未保管」のまま
```

### 3-2. 保管画面

封印済みの箱に対して保管を記録する画面。

**入力項目**

| 項目 | 必須 / 任意 | 内容 |
|------|-----------|------|
| 保管場所 | 必須 | テキスト入力（例：「倉庫2F・棚B」） |
| 保管写真 | 任意 | 保管状況の写真（最大5枚） |

> 保管場所は Phase 1.2 まで封印時に入力していたが、Phase 1.3 から保管時の入力に移動する。

**保管完了時の動作**

- ステータスを `sealed`（未保管）から `stored`（保管中）に更新する
- 保管日時を記録する
- 操作履歴に「保管」を追加する
- グループ共有されている場合、グループメンバー全員に保管通知を送信する

### 3-3. 未保管の箱への保管導線

封印後にその場で保管をスキップした場合でも、後から保管できる。

**導線1：封印一覧から**
- 封印一覧画面で「未保管」の箱をタップ → 箱詳細画面で「保管する」ボタンが表示される

**導線2：QRスキャンから**
- ホーム画面の「中身を確認する」でQRをスキャン → 箱の状態が「未保管」の場合、詳細表示の中に「保管する」ボタンが表示される

## 4. 既存機能への影響

### 4-1. 封印フロー

- 封印完了後に「続けて保管する」「あとで保管する」の選択を追加する
- 封印時の保管場所入力を廃止する（保管時に入力するため）

### 4-2. 封印一覧画面

- ステータス表示を「未保管」「保管中」「開封済み」「破損」の4種類に更新する
- 「未保管」の箱を視覚的に識別できるよう、ステータスバッジの表示を更新する

### 4-3. 箱詳細画面

- ステータスが「未保管」の場合、「保管する」ボタンを表示する
- ステータスが「保管中」の場合、保管日時・保管写真を表示する
- 「開封する」ボタンは「保管中」状態のみ表示する（「未保管」では表示しない）

### 4-4. 確認画面（VerifyPage）

- QRスキャン後の詳細表示で、ステータスが「未保管」の場合に「保管する」ボタンを表示する

### 4-5. 開封フロー

- 「未保管」状態の箱は開封操作を実行できない
- 開封できるのは「保管中」状態の箱のみとする

### 4-6. 通知

- 保管完了時に、グループ共有されている箱のメンバー全員へ通知を送信する

## 5. Phase 1.3 でやらないこと（意図的な除外）

| 機能 | 除外理由 |
|------|----------|
| グループ内チャット機能 | 優先度が低く、設計・実装コストが高い。将来フェーズで対応 |
| 保管場所のQRコードスキャンによる記録 | 現時点の要件ではテキスト入力で十分。将来的に検討 |
| 保管担当者の別途記録 | 操作を行ったユーザーの認証情報から自動的に記録される |

## 6. Phase 1.3 完了の定義

以下の全条件を満たした時点で Phase 1.3 完了とする。

1. ステータス体系が `sealed`（未保管）・`stored`（保管中）・`opened`・`tampered` の4種類になっている
2. 封印完了後に「続けて保管する」「あとで保管する」を選択できる
3. 保管画面で保管場所（必須）と保管写真（任意・最大5枚）を入力して保管を完了できる
4. 封印一覧・箱詳細・確認画面（QRスキャン後）から「未保管」の箱を保管できる
5. 「未保管」状態の箱は開封操作を実行できない
6. 保管完了時にグループ共有されている箱のメンバーへ通知が届く
7. 箱詳細画面に保管日時・保管写真・保管場所が表示される
8. 封印時の保管場所入力が廃止され、保管時に入力する設計になっている
