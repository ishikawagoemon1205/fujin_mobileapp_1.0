## 1. このフェーズの目的

### 何を作ったか

「**封神（Fujin）**」アプリのMVP（最小限で動く製品）を作った。

**「この梱包物は、誰にも開けられていない」ことをデジタルで証明する**アプリ。
Webアプリで発行した専用QRコードシールを梱包物の開閉口に貼ることで封印状態を作り、
シールが破れれば「開封された可能性がある」、全シールが読み取れれば「未開封である」と証明できる仕組みを提供する。

### なぜ作ったか

#### コアの課題：「誰も開けていない」ことを証明できない

現在、梱包物が未開封であることを証明する手段は、ほぼ存在しない。

- **機密情報の運送**: 書類や資料を運ぶ際、途中で誰かに中身を見られていないか確認できない
- **危険物・廃棄物の運送**: 運搬中に中身を抜き取られていないことを証明するのが困難
- **廃棄物処理**: 廃棄物が処理施設に届くまでの間、誰にも開封されていない証拠が残せない
- **貴重品の保管・輸送**: 梱包物の完全性を第三者に説明・証明する手段がない

このような場面では、**物理的なシールだけでは証拠能力が弱く、デジタルによる記録・証明の仕組みが欠けている**。

#### 事業着手の背景：特許技術の転用

クライアント企業は、配送用容器の封印・改ざん検知を目的とした**封印シールに関する特許**を既に保有している。

この特許は封神アプリとは別の事業目的で取得されたものであり、特許そのものがこのアプリ開発の直接的な動機ではない。しかし、特許の核心的な技術思想——「**複数の2次元バーコードを開閉口に分散配置し、読み取り可能な数と個別情報の照合によって未開封性を検証する**」——は、封神が実現しようとする仕組みと本質的に一致している。

> 特許の要点：横長シールに複数QRを印刷し、各QRに識別情報・数量情報・個別情報を持たせる。受領時に残存するQRの数と情報を照合することで、剥がしや破損による開封を検知できる。

この技術的な裏付けがすでに存在すること、そして事業着手の障壁が低いことから、「やってみよう」という判断につながっている。封神は特許技術をスマートフォンアプリとして現代的に再解釈したプロダクトと位置づけられる。

#### サブの価値：中身をすぐに確認できる利便性

封印の証明という仕組みを応用すると、一般の家庭でも使えるメリットが生まれる。

- 引越しや季節の衣替えで「どの箱に何が入っているかわからない」問題を解消できる
- 箱を開けずにスマートフォンで中身を確認できる
- 手書きメモの貼り忘れ・剥がれ・読めなくなる問題をなくせる

### 誰が使うか（Phase 1.0 時点）

封神が提供する価値は2層構造になっており、利用者の属性は幅広い。

| 層 | ユーザー属性 | 得られる価値 |
|----|------------|------------|
| **コア（証明目的）** | 機密情報・危険物・廃棄物を扱う企業・組織 | 「誰も開けていない」ことのデジタル証明 |
| **コア（証明目的）** | 貴重品の輸送・保管を行う事業者 | 物理的完全性の記録と第三者への説明責任 |
| **サブ（利便性目的）** | 引越しや衣替えで多くの箱を保管する個人 | 開封せずに中身を確認できる利便性 |
| **サブ（利便性目的）** | 倉庫管理が必要な小規模事業者 | 荷物管理の効率化 |

> Phase 1.0 ではまず「機能が動く状態」を作ることを優先し、ユーザー認証なしの1人利用シーンで検証する。

## 2. 実装した3つの機能

### 2-1. 封印する

**やりたいこと**: 箱を閉じる前に中身を記録し、QRシールで「封印状態」をデジタル登録する

**使い方の流れ**:

1. ホーム画面で「新しく封印する」をタップ
2. 箱の中身を撮影する（最大10枚）※封印の証拠・内容物の記録
3. メモを書く（例：「冬物の服、毛布類」）
4. 保管場所を入力する（例：「押入れ2F」）
5. 箱を閉じ、開閉口にQRシールを貼って物理的に塞ぐ
6. QRシールをスキャンする（1枚でも複数枚でもOK）
7. 「封印する」ボタンで確定 → この時点から「封印済み」として記録される

**この機能の考え方**:
- **QRシールは開閉口に貼ることが前提**。シールを剥がさずに箱を開けることはできないため、後で「シールが破損している」＝「開封された可能性がある」という証拠になる
- QRシールは箱の複数面に貼れる。面が多いほど封印の強度が上がる（全面塞ぎ）
- 写真は「封印した時点での中身」を証拠として記録するもの。後から「中身が違う」という主張への反証になる
- 保管場所を記録することで「どこに置いたか」の証跡も残せる

### 2-2. 確認する

**やりたいこと**: 箱を開けずに「封印状態」と「中身」を確認する

**使い方の流れ**:

1. ホーム画面で「中身を確認する」をタップ
2. 箱のQRコードを1つスキャンする
3. 箱の情報が表示される
   - **ステータス（未開封 / 開封済み / 破損）← 最重要**
   - 保管場所、封印日時
   - 中身の写真
   - メモ
4. 必要であれば「開封する」へ進める

**この機能の考え方**:
- コアの使い方は「まずステータスを確認する」こと。未開封であることの確認ができれば、内容物の証明として機能する
- 中身の確認は「開封せずに中身がわかる」という利便性としてのサブ価値でもある
- QRは何枚貼ってあっても、どれか1枚をスキャンすればOK（確認は1枚で十分）

### 2-3. 開封する

**やりたいこと**: 箱を開封し、「正規の手続きで開けた」という事実をデジタル記録として残す

**使い方の流れ**:

1. 箱の詳細画面 or 確認画面で「開封する」をタップ
2. 開封手順が表示される
3. 登録した**全て**のQRコードを順番にスキャンする
4. 全て読み取れた → 「**正常開封**」として記録（全シールが無事に存在していた証明）
5. 1枚でも読み取れなかった → 「**破損（tampered）**」として記録（不正開封の可能性）

**この機能の考え方**:
- **全QRが読める＝封印以降に一度も開けられていなかった**ことの証明
- **1枚でも読めない＝開閉口のシールが剥がれた＝途中で開封された可能性がある**という証拠
- 開封時刻がデジタルで記録されるため「いつ・どのような状態で開封したか」が証跡として残る
- これが「封神プロトコル」の核心：物理シールとデジタル記録の組み合わせによるタンパーエビデンス

## 3. 追加で実装した画面

### 3-1. 封印一覧（Box List）📂

- 登録した全ての箱を一覧で表示する画面
- ステータス別に分類表示（封印中 / 開封済み / 破損）
- サマリーカード（封印中○件、開封済み○件）
- タップで箱の詳細画面へ遷移

### 3-2. 箱詳細（Box Detail）📦

- 箱の完全な情報を表示する画面
- 基本情報（Box ID、保管場所）
- 写真ギャラリー（横スクロール、タップで拡大）
- メモ表示
- QRコード情報（登録面数、Face ID一覧）
- 日時情報（封印日時、開封日時、最終確認日時）
- 封印中であれば「開封する」ボタンを表示

## 4. QRコードの仕様

### システム全体の構成

封神は **Webアプリ（QRシール発行）** と **モバイルアプリ（封印・確認・開封）** の2つで成り立っている。

```
[Webアプリ]                         [モバイルアプリ（封神）]
QRコードシールを発行・印刷  →  シールを梱包物の開閉口に貼る  →  アプリでスキャンして封印登録
```

QRシール自体はWebアプリが生成・印刷を担うため、モバイルアプリはスキャン・記録・証明に専念する。

### QRコードのフォーマット

```
fujin://{box-id}/{face-id}/{checksum}
```

| 要素 | 内容 | 例 |
|------|------|-----|
| box-id | 箱の識別ID（8文字、Base62） | `B7K9M3X2` |
| face-id | 面の識別（F1〜） | `F1`, `F2`, `F3` |
| checksum | 改ざん検知用（CRC-16、4文字） | `6D77` |

### なぜこの設計か

- **box-id**: 8文字のランダム文字列。複数のQRシールが「同じ箱のシール」であることを紐付ける
- **face-id**: 箱のどの面（開閉口）に貼ったかを区別。1枚でも破損していれば検知できるよう、面ごとに異なるコードになっている
- **checksum**: QRコードが偽造・コピーされていないことをアプリ内で即座に検証する。改ざんされたQRはchecksum不一致ではじかれる

### チェックサムのアルゴリズム

- CRC-16-IBM（polynomial: 0x8005, reversed: 0xA001）
- Web版（QRシール発行側）とFlutterアプリ（読み取り側）で同一アルゴリズムを実装し、完全一致を確認済み

## 5. データの保存先

### Cloud Firestore（箱の情報）

- 箱のメタデータ（ステータス、保管場所、封印日時）
- QRコード情報（どの面をいつスキャンしたか）← 封印の証跡
- 写真の参照URL ← 封印時点の中身の証拠
- メモ
- 操作履歴（封印・確認・開封のタイムスタンプと詳細） ← 全ての操作を証跡として記録

### Firebase Storage（写真）

- 箱ごとにフォルダを分けて格納
- アップロード時に自動圧縮（品質85%→段階的に下げる）
- 1枚あたり最大2MBに抑制

### 認証

- Phase 1.0 では認証機能なし（匿名アクセス）
- Firebase Security Rulesは全開放状態（MVP開発用）
- **本番リリース前に必ずPhase 2の認証を実装する必要がある**
- ※証明・証跡用途であればユーザーと箱の紐付けが必須となるため、認証は早期に実装する

## 6. 制約事項・制限

| 項目 | 制限値 | 理由 |
|------|--------|------|
| 写真枚数 | 最大10枚/箱 | ストレージ容量とUIの視認性のバランス |
| 写真サイズ | 圧縮後 最大2MB/枚 | モバイル通信環境での実用性 |
| メモ文字数 | 最大1,000文字 | 簡潔な記録を促すため |
| 保管場所文字数 | 最大100文字 | ラベル的な用途のため |
| QRスキャンタイムアウト | 5分 | 開封時の連続スキャンに実用的な時間 |

## 7. Phase 1.0 でやらなかったこと（意図的な除外）

| 機能 | 除外理由 |
|------|----------|
| ユーザー認証・ログイン | MVPでは機能の動作検証を優先した。ただし証明目的の用途では認証は必須となるため早急に対応が必要 |
| オフライン対応 | Firebase直接通信で十分。オフライン同期は複雑度が高い |
| 保管場所の階層管理 | テキスト入力で十分機能する。構造化は実利用データを見てから |
| 検索・フィルタリング | 登録箱数が少ない段階では一覧で事足りる |
| 箱の共有機能 | 機密物の運送・廃棄物管理では複数人への証明共有が必要になるが、まず1人利用の価値検証を先行する |
| 通知・リマインダー | まず基本機能の完成度を優先 |
| 多言語対応 | 日本語ユーザーでの検証が先。証明用途での海外展開は将来の課題 |
| 監査ログ・証明書出力 | 法的・業務的な証明として使うためには記録の改ざん不可性と出力機能が必要。現状はFirestoreの記録のみ |
