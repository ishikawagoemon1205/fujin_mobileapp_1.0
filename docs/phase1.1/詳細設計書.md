## 2. Clean Architecture への完全移行

### 2-1. 設計原則の根拠

このアーキテクチャ設計は **Robert C. Martin（通称 Uncle Bob）** が定義した Clean Architecture の原則に完全準拠する。

#### Robert C. Martin とは誰か

Robert C. Martin は以下の実績を持つ、ソフトウェア設計分野で世界的に最も権威ある人物の一人である。

- **SOLID 原則の提唱者**：オブジェクト指向設計の基本5原則（Single Responsibility / Open-Closed / Liskov Substitution / Interface Segregation / Dependency Inversion）を体系化した
- **アジャイルマニフェスト（2001年）の署名者**：モダンなソフトウェア開発手法の思想的基盤を作った
- **世界的ベストセラーの著者**：『Clean Code』（2008）・『Clean Architecture』（2017）は世界中のソフトウェアエンジニアの必読書
- **50年以上の実務経験**：1970年代から現代まで、実際のシステム開発を通じた知見を発信し続けている

#### なぜこの著者の定義を根拠とするか

Uncle Bob の Clean Architecture 定義は以下の理由から信頼性が高い。

1. **実装ではなく原則を定義している**：特定の言語・フレームワークに依存せず、Flutter / Dart を含むあらゆる環境に適用できる普遍的なルールである
2. **業界標準として広く採用されている**：世界中の Flutter / Android / iOS プロジェクトで採用実績があり、Dart/Flutter コミュニティでも主流のアーキテクチャパターンとなっている
3. **原典が公開・参照可能**：[blog.cleancoder.com](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html) に原文が公開されており、解釈の揺れが生じにくい

#### 唯一の本質的ルール：The Dependency Rule

> *"Source code dependencies can only point inwards."*
> **ソースコードの依存は、必ず内側（抽象度の高い層）にのみ向かなければならない。**

Uncle Bob は「内側の層は外側の層について何も知ってはいけない」と明言している。外側の層のクラス名・関数名・変数名を内側から一切参照してはならない。

これはつまり：

- **Entities（最内層）**：ビジネスルールの中核。何にも依存しない
- **Use Cases**：アプリケーション固有のビジネスロジック。Entities のみに依存
- **Interface Adapters**：データ変換・Presenter・Controller。Use Cases のインターフェースのみに依存
- **Frameworks & Drivers（最外層）**：Firebase・Flutter UI など。全ての詳細はここに閉じ込める

### 2-2. Phase 1.0 の規則違反箇所

Uncle Bob の Dependency Rule に照らすと、Phase 1.0 の構造は以下の点で違反している。

| 違反ファイル | 違反内容 | 対応するルール |
|-------------|---------|--------------|
| `features/*/presentation/*.dart` | Firebase の import が presentation 層に存在する（内側が外側を参照） | Dependency Rule 違反 |
| `features/*/presentation/*.dart` | Firestore ドキュメントの変換ロジックが UI 層に混在 | Interface Adapters の責務が誤った層にある |
| `shared/services/firestore_service.dart` | 複数 feature のデータアクセスが1ファイルに混在し、feature 間の境界が曖昧 | Screaming Architecture（機能の叫び声）原則違反 |
| `shared/services/storage_service.dart` | 同上 | 同上 |
| `features/seal/data/` `features/seal/domain/` | 空ディレクトリが残存（設計の残骸） | — |

### 2-4. 各層の責務定義

| 層 | 依存してよいもの | 絶対に依存してはいけないもの |
|----|----------------|---------------------------|
| `domain/` | Dart 標準ライブラリのみ | Firebase・Flutter・Riverpod 等すべての外部パッケージ |
| `data/` | `domain/`・Firebase パッケージ | `presentation/` |
| `presentation/` | `domain/`・Flutter・Riverpod | Firebase パッケージ（`cloud_firestore` 等）を直接 import 禁止 |

### 2-5. UseCase の設計方針

**UseCase は必ず経由する構成とする。**

`presentation/` は Repository インターフェースを直接呼び出さず、必ず UseCase を経由する。この設計により以下のメリットが得られる。

- ビジネスロジックの置き場所が明確になる（UseCase = アプリが「何をするか」の定義）
- 複数の Repository を組み合わせるロジックを UseCase に集約できる
- presentation 層の責務が「状態管理と表示」のみに絞られる

```dart
// ✅ 正しい依存の向き（presentation → domain → data）
class SealPage extends ConsumerWidget {
  // UseCase を経由してデータにアクセスする
  final createBoxUseCase = ref.read(createBoxUseCaseProvider);
  await createBoxUseCase.execute(params);
}

// ❌ 禁止（presentation が Firebase を直接参照）
class SealPage extends ConsumerWidget {
  final firestore = FirebaseFirestore.instance; // 禁止
}
```

### 2-6. Riverpod の使い方ルール

| 用途 | 使用する Provider |
|------|-----------------|
| Repository の DI | `Provider<T>` |
| UseCase の DI | `Provider<T>` |
| 画面の状態管理（非同期含む） | `AsyncNotifierProvider` |
| 画面の状態管理（同期のみ） | `NotifierProvider` |
| Firebase Auth の状態監視 | `StreamProvider` |

`StateNotifierProvider` は非推奨（Riverpod 2.x 以降は `NotifierProvider` / `AsyncNotifierProvider` を使う）。

## 5. 認証フロー

### 5-1. アプリ起動時の認証ゲート

```
アプリ起動
  │
  └── AuthGate（StreamProvider で Firebase Auth の状態を監視）
        ├── ログイン済み → HomePage へ
        └── 未ログイン  → LoginPage へ（機能画面には一切アクセス不可）
```

### 5-2. メール＋パスワード 認証フロー

```
[LoginPage]
  ├── メール・パスワード入力
  ├── 「ログイン」タップ
  │     ├── SignInWithEmailUseCase.execute()
  │     ├── 成功 → AuthGate が HomePage に遷移
  │     └── 失敗 → エラーメッセージ表示
  │
  ├── 「アカウント作成」リンク → SignUpPage へ
  └── 「パスワードを忘れた」リンク → PasswordResetPage へ

[SignUpPage]
  ├── メール・パスワード・確認パスワード入力
  ├── 「アカウント作成」タップ
  │     ├── SignUpUseCase.execute()
  │     ├── 成功 → AuthGate が HomePage に遷移
  │     └── 失敗 → エラーメッセージ表示
  └── 「ログインに戻る」リンク → LoginPage へ

[PasswordResetPage]
  ├── メールアドレス入力
  ├── 「リセットメールを送信」タップ
  │     ├── SendPasswordResetUseCase.execute()
  │     ├── 成功 → 送信完了メッセージ表示
  │     └── 失敗 → エラーメッセージ表示
  └── 「ログインに戻る」リンク → LoginPage へ
```

### 5-3. Google Sign-In フロー

```
[LoginPage] の「Google でログイン」ボタンタップ
  │
  ├── SignInWithGoogleUseCase.execute()
  │     ├── GoogleSignIn().signIn() でGoogle認証画面表示
  │     ├── GoogleAuthCredential 取得
  │     ├── FirebaseAuth.signInWithCredential() で Firebase 認証
  │     ├── 成功 → AuthGate が HomePage に遷移
  │     └── 失敗 → エラーメッセージ表示（キャンセルの場合はスキップ）
```

### 5-4. ログアウトフロー

```
[HomePage] のログアウトボタン（またはメニュー）タップ
  │
  ├── SignOutUseCase.execute()
  │     ├── FirebaseAuth.signOut()
  │     ├── GoogleSignIn().signOut()  ← Google ログイン時も必ず実行
  │     └── AuthGate が LoginPage に遷移
```

### 6-1. 新規ルート追加

| パス | 画面 | 備考 |

### 6-2. 認証ガードの実装方針

Beamer の `guardNonMatching` または `BeamGuard` を使用し、未認証ユーザーが `/` 以下の画面にアクセスした場合に `/login` へリダイレクトする。

`AuthGate` ウィジェットを `app.dart` のルート直下に配置し、Firebase Auth の `authStateChanges()` を `StreamProvider` で監視することで、ログイン・ログアウト時の画面切り替えをリアクティブに行う。

## 7. Firestore Security Rules の変更

### Phase 1.0（現状：全開放）

```javascript
match /boxes/{boxId} {
  allow read, write: if true;
}
```

### Phase 1.1（認証ユーザーのみ自分のデータを操作可能）

```javascript
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /boxes/{boxId} {
      // 認証済みユーザーかつ自分の箱のみ読み書き可能
      allow read, write: if request.auth != null
                         && request.auth.uid == resource.data.metadata.userId;

      // 新規作成時は userId が自分の UID と一致することを確認
      allow create: if request.auth != null
                    && request.resource.data.metadata.userId == request.auth.uid;
    }
  }
}
```

## 11. テスト方針

Clean Architecture 移行後に以下のテストを追加する。

| テスト対象 | テスト種別 | 理由 |
|-----------|-----------|------|
| 各 feature の UseCase | 単体テスト | `domain/` が Firebase に依存しないため、mock なしでテスト可能 |
| 各 feature の Repository インターフェース | モックテスト | `data/` の実装を mock に差し替えてテスト |
| 認証フロー | ウィジェットテスト | AuthGate の画面切り替えを検証 |

> Phase 1.0 では「Firebase 依存のため Widget テストを保留」としていたが、Clean Architecture 移行後は domain 層が Firebase から独立するため、単体テストが書けるようになる。これが移行の主要なメリットの一つである。
