## 1. このフェーズの目的

### Phase 1.1 とは何か

Phase 1.0 で「機能が動く状態（MVP）」を作った。Phase 1.1 はその基盤を**本番運用に耐える品質**に引き上げるフェーズである。

Phase 1.0 では意図的に後回しにした以下の3点を、このフェーズで一括して解決する。

| タスク | 概要 |
|--------|------|
| **① Clean Architecture への完全移行** | 保守性・テスタビリティを確保するアーキテクチャへ刷新 |
| **② ルートドキュメント整理 ＋ README 一新** | 開発実態と乖離したドキュメントを削除・整理 |
| **③ ユーザー認証・登録機能の実装** | Firebase Auth によるEmail認証・Google認証の実装 |

### なぜ今やるか

封神は「誰も開けていない」ことのデジタル証明を提供するアプリである。

証明の信頼性を担保するためには、**「誰が」封印・開封したかを紐づけるユーザー情報が不可欠**である。Phase 1.0 は匿名アクセスで機能検証を行ったが、実用に供するためには認証を軸にしたデータ管理への移行が必須となる。

認証実装に合わせて、アーキテクチャの刷新（Clean Architecture移行）とドキュメントの整理を同時に行うことで、Phase 2 以降の機能追加をスムーズに進められる基盤を確立する。

## 2. タスク ① Clean Architecture への完全移行

### 2-1. 目的

Phase 1.0 では、Firebase へのアクセスを `shared/services/` に集約し、各 feature の `presentation/` がそれを直接呼び出す「Fat Presentation Layer」の構造をとった。

この構造の問題点は以下の通りである。

- Firebase を別のバックエンドに差し替えた場合、UI層にまで変更が波及する
- ビジネスロジックが UI 層に混在しており、単体テストが困難
- 機能間の依存関係が暗黙的になりやすく、変更影響の範囲が読みにくい

これらを解消するため、**アーキテクチャをスクラップアンドビルドで刷新する**。

### 2-2. 移行方針

- 段階的移行ではなく、**全 feature を一括でリファクタリング**する
- Phase 1.0 の動作は維持しつつ、内部構造を Clean Architecture の3層（`presentation/domain/data`）に再編する
- 移行完了の定義は「**2-3. Clean Architecture の完了定義**」に従う

### 2-3. Clean Architecture の完了定義

#### 根拠となる原典

この完了定義は **Robert C. Martin（通称 Uncle Bob）** が定義した Clean Architecture の原則に基づく。

> Robert C. Martin は、アジャイルソフトウェア開発の第一人者であり、SOLID 原則の提唱者。世界的ベストセラー『Clean Code』『Clean Architecture』の著者として、ソフトウェア設計の分野で最も権威ある人物の一人。

原典記事：[The Clean Architecture — Clean Coder Blog (2012/08/13)](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)

#### 唯一の本質的ルール：The Dependency Rule

Uncle Bob が定義した Clean Architecture の中核は **Dependency Rule（依存関係のルール）** の1点のみである。

> *"Source code dependencies can only point inwards."*
> **ソースコードの依存は、必ず内側（抽象度の高い層）にのみ向かなければならない。**

内側の層は、外側の層について何も知ってはいけない。外側の層のクラス名・関数名・変数名を、内側の層が一切参照してはならない。

#### Uncle Bob が示す Clean Architecture の5つの特性

| # | 特性 | 意味 |
|---|------|------|
| 1 | **Independent of Frameworks** | ビジネスルールがフレームワークに依存しない |
| 2 | **Testable** | DB・UIなしでビジネスルールを単体テストできる |
| 3 | **Independent of UI** | UIを変更してもビジネスルールに影響しない |
| 4 | **Independent of Database** | DBをFirestoreから別サービスに替えられる |
| 5 | **Independent of any external agency** | ビジネスルールは外部の世界を知らない |

#### 封神における具体的な完了条件

上記の Dependency Rule と5特性に基づき、封神の完了定義を以下の通り定める。

**条件1: 3層構造の確立**

全 feature が `presentation/` ・ `domain/` ・ `data/` の3層を持つ。

**条件2: domain 層の Firebase 独立**

`domain/` 内のコードに `import 'package:cloud_firestore/...'` および `import 'package:firebase_storage/...'` が **1行も存在しない**。

**条件3: domain 層の Flutter 独立**

`domain/` 内のコードに `import 'package:flutter/...'` が **1行も存在しない**（純粋な Dart コードである）。

**条件4: presentation 層の Firebase 非依存**

`presentation/` 内のコードが Firebase を直接参照しない。アクセスは必ず `domain/` が定義する Repository インターフェースまたは UseCase を経由する。

**条件5: shared/services の廃止**

`shared/services/` ディレクトリ（`firestore_service.dart`, `storage_service.dart`）を廃止し、Firebase アクセスを各 feature の `data/` 層に分散する。

#### 現状（Phase 1.0）の規則違反箇所

| 違反箇所 | 内容 | 対応する完了条件 |
|---------|------|----------------|
| `features/*/presentation/*.dart` | Firebase を直接 import・呼び出し | 条件2・条件4 |
| `shared/services/firestore_service.dart` | Firebase アクセスが共有サービスに集約（feature に属していない） | 条件5 |
| `shared/services/storage_service.dart` | 同上 | 条件5 |
| `features/seal/data/` `features/seal/domain/` | 空ディレクトリのまま残存（実装なし） | 条件1 |
| 各 feature の `domain/` `data/` | 未作成 | 条件1 |

## 4. タスク ③ ユーザー認証・登録機能の実装

### 4-1. 認証方式

| 方式 | 採用理由 |
|------|----------|
| **メールアドレス ＋ パスワード** | 汎用性が高く、全ユーザーが利用できる標準的な認証 |
| **Google アカウント ログイン** | パスワード管理不要でユーザー体験が向上し、セキュリティも高い |

### 4-2. 認証ガードの方針

**未ログインユーザーは機能を一切使えない。**

アプリ起動時に認証状態を確認し、未ログイン状態であればログイン画面に強制リダイレクトする。ホーム画面を含む全ての機能画面にアクセスできない。

### 4-3. 既存データの扱い

Phase 1.0 で登録されたデータはテストデータとして扱い、マイグレーションは行わない。Phase 1.1 から新規登録されるデータは全て認証済みユーザーの `userId` に紐付ける。

### 4-4. 実装する画面

| 画面 | 概要 |
|------|------|
| **ログイン画面** | メール・パスワード入力 ＋ Google ログインボタン。パスワードリセットへのリンクあり |
| **サインアップ画面** | メール・パスワード入力による新規アカウント作成 |
| **パスワードリセット画面** | メールアドレスを入力するとリセットメールを送信 |
| **ホーム画面（更新）** | ログアウト機能を追加 |

### 4-5. パスワードリセット

Phase 1.1 に含める。Firebase Auth の `sendPasswordResetEmail` を使用。

### 4-6. 認証後のデータ紐付け

封印登録時、Firestore の `boxes/{boxId}` ドキュメントに `userId` フィールドを追加する。Firestore Security Rules もユーザー認証ベースに変更し、自分の箱のみ読み書き可能にする。

## 5. Phase 1.1 でやらないこと（意図的な除外）

| 機能 | 除外理由 |
|------|----------|
| ソーシャル認証（Apple, LINE 等） | Google Sign-In で十分。複数認証方式は後から追加容易 |
| 既存データのマイグレーション | テストデータのため不要。実コストに見合わない |
| オフライン対応 | 認証が絡む場合のオフライン同期は複雑度が高い |
| メールアドレス確認（sendEmailVerification） | 登録後にメールアドレスの実在確認メールを送る機能。UX の障壁になるため後回し。実用ユーザーが出てから検討。メールアドレス＋パスワードによるアカウント作成・ログイン自体は実装する |
| 多要素認証 | Phase 2 以降での対応 |

## 6. Phase 1.1 完了の定義

以下の全条件を満たした時点で Phase 1.1 完了とする。

1. Clean Architecture の完了条件（条件1〜5）を全て満たしている
2. 削除対象の3ファイルがリポジトリから除去されている
3. `README.md` が現行の実装を正確に反映した内容に更新されている
4. メール＋パスワード認証・Google認証が動作する
5. パスワードリセット機能が動作する
6. 未ログインユーザーが機能画面にアクセスできない（認証ガードが機能している）
7. 新規封印データに `userId` が紐付いて保存される
8. Firestore Security Rules が認証ユーザーのみ自分のデータを読み書きできるルールになっている
